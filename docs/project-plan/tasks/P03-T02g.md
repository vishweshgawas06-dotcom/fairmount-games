# P03-T02g — Defensive account-change session invalidation

**Status:** Implemented; PostgreSQL CI pending (2026-10-19).

D-03 requires immediate revocation on disablement, password change/reset and owner MFA recovery. Migration `20261019_05` installs PostgreSQL AFTER UPDATE triggers: ENABLED → DISABLED status changes revoke unrevoked sessions for that account; any changed `password_hash` revokes its sessions; and replacement/confirmation changes to owner MFA key version, nonce, ciphertext or confirmation timestamp revoke owner sessions. Each update happens inside the same transaction as its triggering change. For a corrupt future-issued row, the revocation timestamp is at least `issued_at` so the session ceases to count as active. Updating only an ordinary password-change timestamp, re-saving unchanged status, or accepting a TOTP step does **not** invalidate sessions. Recovery-code **consumption during login/step-up** is not factor replacement and does not trigger revocation.

**Limits:** This is a DB backstop, not account-change authorization, an actor/reason audit, a complete MFA recovery/reset flow, or realtime socket closure. A later service must authenticate the actor, check scope and owner MFA recency, record reason/audit and commit the account/credential/factor change; a separately reviewed recovery-code *rotation* path (not ordinary consumption) must explicitly revoke sessions if it doesn't replace the encrypted factor. Already-connected realtime clients must revalidate frequently and stop receiving private data after revocation. D-02 retention/backup policy remains undecided. There is no public route and no bypass of lost owner factors.
