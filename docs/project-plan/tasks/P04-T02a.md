# P04-T02a — Opt-in direct-TLS self-wallet read boundary

**Status:** Local Ruff/unittest passed; Python 3.12/PostgreSQL CI pending. Disabled behind this proxy preview; not gameplay or a general wallet API.

`GET /api/v1/me/wallet` reads **only the account named by the currently validated session**. It accepts no account or player ID in its path/body/query. A configured direct-TLS deployment must provide a real HTTPS peer, exact Host, no forwarded headers and no cross-site `Origin` or `Sec-Fetch-Site` assertion. The session cookie's *shape* is checked at the edge; the private PostgreSQL projection then checks live session expiry/revocation, enabled account status and role, pins the account lock and reads only the actor's wallet. The session touch commits before emitting a minimal account ID/balance response. Disabled/revoked/missing sessions give generic 401; missing transport, schema or DB configuration gives generic 503. Responses are no-store, `Vary: Cookie` and `nosniff`. The route remains unreachable through the normal HTTP preview configuration.

HTTP tests cover disabled/default/HTTP, missing or duplicate cookies, cross-site/forwarded headers, rejected account-ID queries, generic DB/session failure and exact response fields. PostgreSQL tests cover OWNER, AGENT and PLAYER self balances, unknown tokens and a disabled player. These do not yet prove a full committed HTTP login→wallet→logout integration across independent connections, browser CORS/CSRF for future point mutations, dashboard assignment scope at the API edge, or reverse-proxy safety. No cross-account wallet API is exposed.
