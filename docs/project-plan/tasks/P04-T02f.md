# P04-T02f — Direct-TLS live dashboard ID roster and owner audit gate

**Status:** Implemented; local HTTP/Ruff checks passed. PostgreSQL CI pending. Not enabled in the proxy preview.

`GET /api/v1/me/players` accepts no query parameters or client-selected role/agent. It uses the existing direct-HTTPS, exact-host, no-forwarded-headers, same-site safe-GET boundary and one live session transaction. The existing transaction-scoped roster service returns **only IDs**: OWNER sees all enabled PLAYERs, AGENT only currently assigned enabled PLAYERs, and PLAYER only self. It locks/rechecks targets before the transaction commits, including reassignment and disablement. Revoked/disabled sessions receive generic 401; missing direct-TLS/schema/database configuration receives generic 503. Response headers are no-store, `Vary: Cookie`, and `nosniff`. A roster ID is **not** authorization for a subsequent wallet/bet request; each resource must recheck its own current scope.

HTTP adapter tests cover disabled mode/HTTP transport, missing or duplicate cookies, cross-site/forwarded assertions, query tampering, projected ID-only payload and generic errors. Committed PostgreSQL tests cover player self roster, agent cross-assignment, reassignment/disablement, and OWNER omission of a disabled player while the owner may still read that player's wallet as an existing financial claim. The owner and agent sessions used for these scoped read tests are seeded under DB constraints; they do **not** prove owner MFA enrollment/login or agent login over HTTP. Existing pure data-layer tests cover owner/player/agent scopes. Full UI, private field exposure, a bounded/paginated large roster contract, owner password/MFA login acceptance, reverse-proxy trust, and gameplay-write CSRF remain open. The preview stays non-playable and cannot authenticate.
