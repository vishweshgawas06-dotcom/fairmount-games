# P06-T01b — opt-in owner lifecycle HTTP writes and replay receipts

Status: **implemented and tested; direct-TLS lab only, not full registration or P06 completion.**

## Scope and contract

Five `POST` routes are wired into the API, disabled unless the existing
`direct-tls` edge configuration is explicitly supplied:

| Route under `/api/v1/operator/` | Strict JSON body | First success |
|---|---|---|
| `agents` | `{}` or `{"agent_id":"AGT-…"}` | 201, account ID, Agent ID, setup secret and expiry |
| `players` | `{"username":"…"}` | 201, account ID, username, setup secret and expiry |
| `assignments` | `{"username":"…","agent_id":"AGT-…"}` | 200, assignment ID |
| `assignments/remove` | `{"username":"…"}` | 200, unassigned |
| `accounts/status` | `{"identifier":"…","enabled":true}` | 200, resulting status and role |

Every request needs direct HTTPS, the configured canonical Host/Origin, no
forwarding headers, a session cookie, matching double-submit CSRF cookie/header,
a nonzero UUID `Idempotency-Key`, a bounded JSON object (4096 bytes maximum), and
no ambiguous headers or duplicate fields. Unknown fields, null text fields,
non-string identifiers and non-boolean flags are rejected. The route uses the
existing write boundary rather than introducing a second parser.

## Authorization, audit and locking

Inside the attempt guard, authenticate a live owner and require MFA verified
within ten minutes **before resolving identifiers or reading a replay receipt**.
The P06-T01a services repeat their locked role/status checks. Agents and players
cannot invoke any route. The sole owner is never a status target.

The existing pseudonymous write windows count attempts, including denials:
20/minute/session and 120/minute/source, shared with gameplay writes. This is a
conservative lab budget, not a newly approved production capacity policy.
Exhaustion returns 429 plus `Retry-After`; malformed envelopes are 401, invalid
body schemas 400, authorization/business denials 403, key conflicts 409 and
configuration/database failures 503. Replies never reflect denied identifiers,
credentials or SQL diagnostics.

Assignment now locks **owner → destination agent → player → assignment**, to
match agent transfer's **agent → player** order. It previously took the player
before the agent, which could deadlock with an allocation. Reassignment ends the
prior row and retains historical attribution. Disablement relies on the existing
D-03 triggers to revoke sessions atomically. Assignment/enable repeats with a
new request key still produce no duplicate state-change audit event.

## Replay and secret delivery

Migration `20261103_03` introduces `operator_write_receipts`, keyed by owner and
request UUID. A receipt stores a deterministic command/body digest and the
**non-secret** success payload. The locked owner serializes simultaneous
requests, including generated-Agent-ID retries. The action, audit and receipt
commit together. Expected denials roll back their savepoint while the attempt
counter commits; database failures roll back the outer transaction.

- Same key + same command: 200 with `replayed: true`; no action is executed.
- Same key + different command/body: 409; nothing changes.
- First success: `replayed: false`; creation returns the setup secret once.
- Creation replay: same account reference and expiry, **no `secret` field**.
  This remains true after concurrent retries or a later account mutation.
- Revoked/stale owner sessions cannot read even their own replay receipt.
- A historical disable replay cannot disable an account that was subsequently
  enabled by another command.

Receipts reject a top-level `secret`, cannot be updated/deleted/truncated, and
migration downgrade refuses to discard populated receipts. They do not store
passwords or bearer tokens. Responses use `no-store`, `no-cache`, `Vary: Cookie`
and `nosniff`, and are rendered only after commit.

**Lost response limitation:** if the first creation response is lost, retry
acknowledges the existing account but cannot recover its secret. Do not create a
second account to work around this. A separately authorized pending-credential
reissue flow is still required before registration can ship. Clients must not
blindly retry with a fresh key, especially when creating generated Agent IDs.

## Tests and evidence

`tests/test_zz_operator_api.py`: 13 cases, including fail-closed defaults,
committed creation/digest-only storage, non-secret replay, body/action conflicts,
assignment history and audit, disable/session revocation, historical replay,
owner recency/role denials, strict schemas, CSRF/origin/forwarded-header denials,
duplicate identifiers without receipts, denied-attempt throttling, concurrent
same-key generated Agent creation (one account/one secret delivery), revoked
replay denial, receipt immutability/no-secret constraints, and injected receipt
failure rolling back the entire action.

Local verification:

- Fresh PostgreSQL: **301 unittest cases, 0 skips**.
- Separate fresh PostgreSQL: **390 pytest cases passed**.
- Upgrade → downgrade base → upgrade head and `alembic check`: no drift.
- Downgrade with committed receipts correctly refused; revision stayed at head.
- CI pure domain suite, Node wheel suite, Ruff and Markdown link checks run at
  the checkpoint; GitHub CI evidence is recorded after push.

## Still open

No member activation/reissue HTTP flow, required registration name/mobile fields,
agent-created *assigned* players, operator dashboard, wallet write routes,
reason/retention policy or trusted-proxy deployment. The owner-only functions in
this slice do **not** replace D-10's approved agent-created player capability:
that remains a P07 implementation requirement. These are restricted lifecycle
adapters, not complete registration and not production acceptance.
