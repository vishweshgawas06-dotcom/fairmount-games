# P03-T03a — member activation and pending setup-secret recovery

Status: implemented and tested, **opt-in direct TLS only**; not production registration.
Date: 7 November 2026.

## Scope and acceptance

- `POST /api/v1/auth/activate`: exact JSON fields `role` (`AGENT` or `PLAYER`),
  `identifier`, `secret`, `new_password`. Requires configured direct HTTPS,
  canonical Host/Origin, no forwarded identity, bounded 4096-byte UTF-8 JSON,
  unique fields, one Content-Length, no content/transfer encoding or query.
- No session cookie is needed: authorization is possession of the valid pending
  setup secret, not ambient owner/member session state. Cross-origin requests
  are refused. **No session/cookie is issued** after activation; ordinary guarded
  member login is a separate operation. Owner activation remains local only.
- Account → Credential locks serialize activation/reissue/disablement. Verify
  enabled role and canonical identifier; consume a valid unexpired setup secret
  once. Expiry is rechecked after hashing with the PostgreSQL clock. Clear the
  verifier/expiry and store Argon2id + consumed/password-change times atomically
  with `INITIAL_CREDENTIAL_CONSUMED` self-service audit.
- Passwords use the existing 12–128-character Unicode/spaces policy without
  trimming or changing case, with obvious-password rejection. A wrong, expired,
  used, disabled or missing credential, wrong role, weak password or throttled
  attempt gives the same generic 401. Malformed schemas give 400;
  configuration/database failure gives 503, never a fabricated proof denial.
- The existing DB-backed authentication guard adds the `MEMBER_ACTIVATION`
  surface: 5 subject failures / 15 minutes, 30 source failures / 15 minutes.
  Keys are HMACs; failures and throttles commit without raw credentials,
  identifiers or addresses. Expensive hashing is skipped when blocked.

## Lost setup-response recovery

`POST /api/v1/operator/accounts/setup-secret`, exact body `{"identifier":"…"}`,
uses the owner write envelope, CSRF, recent owner MFA, attempt budgets and atomic
replay receipts. Rotate **only pending** enabled agents/players, including expired
pending secrets; never an active password or the owner. A fresh 24-hour verifier
replaces the old one and `INITIAL_CREDENTIAL_REISSUED` records the actual owner
and target. The new secret appears only on first success, never in the receipt.
Same-key replay cannot rotate again; changed commands conflict. If that response
is also lost, a new authorized reissue command can rotate again. Agents cannot
reset or reissue player credentials through this route.

This is pending-credential recovery, **not** password reset, MFA recovery,
self-registration, mobile-based identity verification or an agent reset grant.
Profile fields and complete agent-created player registration remain separate.

## Migration / rollback

`20261107_01` extends the two check constraints for the activation failure
surface and reissue event; metadata and readiness revision match. Downgrade
refuses when the new audit rows exist. No credential or failure audit is deleted
for rollback. The caller owns the outer transaction, and secrets are delivered
only after successful commit.
