# P11-T03a — opt-in direct-TLS player bet write

Status: **implemented and tested; disabled by default and not deployed.**

## Scope

Connects the P03-T02p gameplay-write envelope to the existing POOL-01 admission
service through one guarded route:

`POST /api/v1/rounds/{round_id}/bets` →
[same-origin envelope](../auth/GAMEPLAY_WRITE_CONTRACT.md) → strict
[bet body schema](../../../services/api/src/fairmount_api/roulette/bet_request.py)
→ `place_bet()` (reserve-serialized admission, caps, wallet and idempotency) →
single committed transaction → `{"bet_id", "requested", "accepted", "unaccepted",
"replayed"}` with `Cache-Control: no-store` and `Vary: Cookie`.

Guards, in order:

1. `_direct_source()` — `FAIRMOUNT_AUTH_EDGE_MODE=direct-tls`, an `https` ASGI
   scheme, a canonical `FAIRMOUNT_PUBLIC_ORIGIN`, exact `Host`/`Origin`, no
   `Forwarded`/`X-Forwarded-*`/`X-Real-IP` header and a real transport peer. Any
   other configuration returns 503.
2. `require_gameplay_write()` — `POST` only, no query string, one bounded JSON
   body, double-submit CSRF, one normalized `Idempotency-Key`.
3. Canonical UUID round path (non-canonical or unknown targets are generic).
4. `parse_bet_request()` — exactly `selection_key` and `stake`; canonical
   catalogue selection; chips 5/10/50/100/500 up to `2^63-1`.
5. `place_bet()` — live PLAYER session, open round before cutoff, **full** stake
   affordability, per-number/per-selection caps, global worst-payout and
   full-void-refund reserve coverage, then paired ledger + bet insert.

`Idempotency-Key` is passed to `place_bet`, which persists it on
`point_operations` with a request fingerprint. A replay of the identical intent
returns the original bet (`replayed: true`) with no second debit; the same key
with a different selection, stake or round is a 409 `conflict`. Equivalent
selection spellings (`split:20-17` / `SPLIT:17-20`) share one fingerprint.

## Tests

- `tests/test_bet_request_schema.py` (pure, 8 cases): canonical intents, equivalent
  spellings, unknown/missing/extra fields, non-object bodies, boolean/float/string
  /out-of-range stakes, invalid and oversized selections, error text that never
  echoes the value.
- `tests/test_zz_player_bet_api.py` (PostgreSQL + HTTP, 9 cases): one accepted bet
  debits the wallet and credits the reserve exactly once; same key replays without
  a second debit; changed request conflicts; equivalent spelling replays; wrong
  origin, missing CSRF, missing key, query string, form body, extra field, bad chip,
  invalid selection and oversized body all write nothing; unaffordable full stake is
  rejected with no partial acceptance; unknown/non-canonical round IDs are generic;
  only `POST` is routed; the route is 503 without direct-TLS configuration.
- The module is named `test_zz_` (after the existing committed `test_z_` flows)
  because accepted bets, ledger rows and the single OWNER row are immutable; it
  reuses an existing OWNER when an earlier committed module created one. Run the
  suite on a freshly recreated test database
  (`python -m infrastructure.reset_test_db --yes` then `alembic upgrade head`).
