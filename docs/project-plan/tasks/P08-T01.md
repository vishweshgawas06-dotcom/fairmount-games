# P08-T01 — Integrate pure roulette catalogue, payout and cap rules

**Status:** Pure implementation complete (2026-10-20); [Python 3.12/PostgreSQL CI 39908224792](https://github.com/vishweshgawas06-dotcom/fairmount-games/actions/runs/39908224792) passed on `3e11649`. No database integration or public betting route.

The merged PR #2 has reusable domain rules but an incompatible BIGINT account model, migration history and unapproved wallet/recovery services. This checkpoint ports only `roulette/catalogue.py`, `payout.py`, `caps.py` and typed `core/errors.py` from that PR into the existing UUID identity branch. The fixture `tests/fixtures/roulette_catalogue.json` remains byte-identical across both branches; identity models/migrations remain untouched. The approved unusual **total** payout convention is preserved (10 straight-up → 350 credited total, not 360), with bool/float and invalid outcomes rejected by the pure payout helper. Cap arithmetic does not decide cap scope, authorize callers or debit balances.

`reserve_coverage.project_round_exposure` uses server-validated canonical selection keys and valid 5-point-unit stakes to construct the 37 total-payout outcomes and full void refund from a supplied list of accepted bets, including a candidate if supplied. It is a **pure** bridge to POOL-01, not a bet admission service: only a future locked database transaction can ensure a candidate appears exactly once and that accepted bets/funding did not change concurrently. It does not touch the RNG, wallets, database, round clock or routes. Existing `reserve_can_accept` still requires a separately funded, atomic reserve.
