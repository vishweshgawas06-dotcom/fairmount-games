# P11-T01a — Private, reserve-serialized POOL-01 bet admission

**Status:** Internal implementation/local non-DB gates complete (2026-10-23); PostgreSQL CI pending. No public bet route, settlement, rebet, round worker or live game.

`roulette.admission.place_bet` takes only an existing player session token, UUID round ID, server-validated canonical legal position, full requested 5-point-unit stake and actor-scoped idempotency key under a caller-owned PostgreSQL transaction. It locks player Account/session → **global reserve** → round → player wallet and checks the database clock after the round lock; the bet-insert trigger independently rechecks cutoff. The **full requested stake** must be affordable before cap partial acceptance. Straight/split stake is bounded by each included number's existing per-player/round 2,000 exposure; other selections by the exact canonical per-player/round 2,000 cap. The nonaccepted cap remainder is **never debited**; no wallet-limited or reserve-limited partial bet is made.

For the cap-approved candidate, the service rebuilds all unsettled rounds' 37-number total payout vectors and full void refunds from **persisted bets**, appends the candidate exactly once and applies approved POOL-01 `sum(max(highest payout, full void refund))`. Only if the existing reserve plus the proposed stake covers that global liability does it write an idempotent `BET_STAKE` operation, paired player→reserve journal entries and an immutable accepted-bet row. Concurrent callers must lock the reserve before this calculation; it never affects the independently generated winning number. Existing accepted bets stay unchanged if a candidate cannot be funded. Same-key/same-request replay reports the original accepted amount/ID even after cutoff; changed intent conflicts. A caller must commit successfully **before** confirming acceptance to a player and roll back any DB error.

**Still unsafe for a public betting release:** there is no API/cookie/CSRF/auth failure audit/rate-limit boundary, reserve withdrawal service, settlement/void service, cap-exposure performance validation, global reserve/bet multi-connection race, persisted terminal-obligation reconciliation or D-06 worker/recovery. The database's privileged role can directly insert rows; do not grant that role to a production application or expose the internal service until authorization and funding/settlement gates pass. The transaction rebuilds all unsettled bet vectors on every candidate; performance under production load is unmeasured.
