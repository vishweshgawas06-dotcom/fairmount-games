# P06-T01a — owner provisioning and account lifecycle services

Status: **implemented and tested as internal services; no HTTP route, no UI.**

## Why

Every phase after this one needs operators to exist before it can be wired:
P07 cannot scope an agent to "its" players until a player can be assigned, P04's
HTTP slices can only exercise sessions that were created out of band, and P10's
dashboards have nothing to list. This is the smallest slice that makes the
D-01 account model real — one owner, agents created by that owner, players
created by that owner, and an audited assignment between them — without opening
a privileged endpoint.

## What it is

### Provisioning (`identity/provisioning.py`)

`provision_agent(connection, owner_token, agent_id=None)` and
`provision_player(connection, owner_token, username=...)`:

- **Owner-only, recent-MFA.** Both call `require_recent_owner_mfa` (proof no
  older than ten minutes) and then re-read the caller's `Account` row with
  `FOR UPDATE`. A session that a concurrent disablement revoked, or a token
  belonging to an agent or player, fails closed with one generic
  `ProvisioningUnavailable`. An agent cannot create a sub-agent through this service because the
  caller's *role* is re-checked under the lock, not inferred from the token.
- **Fixed Agent IDs.** An explicit Agent ID is validated with
  `canonical_agent_id`; otherwise an ID is generated and a collision re-rolls
  (bounded attempts) so a collision never leaves a half-created account. Player
  usernames go through `canonical_player_username`, which rejects reserved names
  (`admin`, `owner`, `support`, `system`, `root`), the `agt-` namespace, bad
  characters and out-of-range lengths.
- **One-time secret, digest only.** A 24-hour initial secret is returned once in
  a `ProvisionedMember` whose `secret` field is `repr=False`, to reduce accidental disclosure in object representations. Callers must still
  avoid logging the field or a serialized response. Only `initial_secret_digest` is stored, the
  password hash stays null, and the member therefore cannot authenticate until it
  consumes the secret and sets a permanent password (P03 activation policy).
- **Atomic.** Account, private identity, pending credential and one
  `INITIAL_CREDENTIAL_ISSUED` audit event commit or roll back together; the audit
  row carries the actor, the target and the source only.

### Assignment and enablement (`identity/account_admin.py`)

- `assign_player(...)` locks in the documented order (owner `Account` → agent
  `Account` → player `Account` → assignment row; corrected in P06-T01b), refuses a disabled or
  wrong-role target, ends any previous row with `ended_at` and appends
  `AGENT_UNASSIGNED` before inserting the new row and `AGENT_ASSIGNED`. Two
  calls for the same pair are idempotent and produce no extra history.
- `unassign_player(...)` closes the current row and returns `False` when there
  was nothing to close; it never deletes history.
- `set_account_enabled(...)` toggles only `AGENT`/`PLAYER` — the sole `OWNER`
  can never be disabled through this path — writes `disabled_at`, appends one
  event, and is idempotent (a repeat returns the current status and adds no
  duplicate event). Live sessions of the disabled account are revoked by the
  existing D-03 database triggers inside the same statement, so no token is ever
  handled by this module.
- Every denial is the same generic message, so callers cannot use these
  functions to probe which IDs exist.

### Migration `20261103_02`

Adds exactly four event types (`ACCOUNT_ENABLED`, `ACCOUNT_DISABLED`,
`AGENT_ASSIGNED`, `AGENT_UNASSIGNED`) to `ck_security_events_valid`. The table
stays append-only and still requires an actor, a non-null target and an approved
source. The downgrade raises rather than narrowing the constraint while such
rows exist.

## What it is not

No route, no cookie, no CSRF handling, no rate limiting, no "reason" field
(D-02 retention is still undecided), no member activation endpoint, no agent-side
player creation, no transfer or wallet action, and no dashboard. Nothing here is
reachable from the preview, so disabled-write and private-read rules are
unchanged. It is also not P07 authorization: the assignment rows are the input
to that scope, not proof that a route checks them.

## Tests

`tests/test_operator_lifecycle.py` (13 PostgreSQL cases, rollback-isolated, one
rolled-back owner per test so a fresh environment can still bootstrap its own):

- **Provisioning:** a generated Agent ID matches `AGT-[A-Z2-9]{10}` and is stored
  lowercase; the stored digest equals the digest of the returned secret and is
  not the secret; `password_hash` stays null; exactly one
  `INITIAL_CREDENTIAL_ISSUED` event; neither the secret nor any derived value
  appears in the audit row; a fixed Agent ID is honoured and duplicates,
  malformed IDs and out-of-namespace IDs are refused; player usernames are
  canonicalised, reserved/duplicate/malformed names refused; a freshly
  provisioned member cannot log in; owner tokens that are missing, unknown or
  45 minutes past their MFA proof are refused; agent and player sessions cannot
  provision.
- **Assignment:** the row records the actor; assigning the same pair twice
  creates one row; reassignment leaves exactly one open row, two rows total, and
  the event counts `AGENT_ASSIGNED ×2` / `AGENT_UNASSIGNED ×1`.
  `unassign_player` returns `True` then `False`.
- **Denials:** a player or owner ID as the agent, a random UUID, a non-UUID, a
  role mismatch, a disabled agent and a stale-MFA token are all refused.
- **Enable/disable:** disabling a player revokes its live session (verified by
  digest), sets status `DISABLED` and `disabled_at`, and appends
  `ACCOUNT_DISABLED`; re-enabling clears `disabled_at`, and a repeat adds no
  second event; the sole owner cannot be disabled or targeted; non-boolean
  `enabled` values and unknown IDs are refused.

## Remaining gates

Provisioning/assignment/enable HTTP routes with cookies and CSRF, an activation
route that consumes the one-time secret and enforces the D-13 password policy
with rate limiting, the "reason" contract for account actions (D-02), owner
dashboards (P06-T02), agent-scoped reads and allocations (P07) and the proxy/IP
decision that any rate limiting depends on.
