# P03-T01q — Owner-only local development setup CLI

**Status:** Implemented; Python 3.12 CI pending (2026-10-19).

**Authorization:** Owner approved personally running a deployment-only local setup command (D-12), fixed `owner` login label (D-14), 24-hour initial secret, ten recovery codes and external MFA key (D-15). This slice connects the tested internal transactions to a **terminal-only, local `fairmount_dev` CLI**; it is not a production deployment adapter, browser endpoint, login or session.

## Implementation

- `python -m fairmount_api.identity.owner_setup_cli {init,reissue,activate,enroll,confirm}` requires interactive stdin/stdout/stderr TTYs and explicit `FAIRMOUNT_DB_NAME=fairmount_dev`; existing DB URL is localhost-only. It refuses redirected non-interactive execution; it cannot detect a terminal recorder, so operator procedure remains essential. No secret/password/code is accepted on the command line. `activate` and `confirm` read hidden terminal input; `enroll`/`confirm` require the restricted versioned MFA key file.
- Every operation uses a PostgreSQL transaction. Initial secret, authenticator seed and ten offline codes are emitted **only after** the transaction commits; errors never include SQL bind parameters or secrets. The post-commit delivery-failure message warns that DB state may have changed and any partial terminal output is sensitive. CLI tests use fake transactions/terminal streams to verify TTY/database guards, post-commit ordering, no error leaks and failure paths; underlying PostgreSQL service tests already cover atomic state changes.
- [Owner setup safety notes](../auth/LOCAL_OWNER_SETUP.md) document local-only limits and the unresolved lost-output/retry risks. An owner who loses an already displayed unconfirmed TOTP seed cannot currently reset that factor; codes are displayed once after confirmation. Do **not** claim production readiness or owner dashboard access.
