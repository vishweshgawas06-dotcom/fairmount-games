# P09-T02a — public reveal-only event stream

Status: **implemented and tested; public, read-only, not a gameplay feed.**

## Why

The only realtime delivery was client polling of `GET /api/v1/roulette/round`.
A player UI that polls cannot show the wheel phase change or the reveal at the
right moment without guessing, and more clients polling means more queries.
This slice adds one server-driven stream with the same reveal-safety rules.

## What it is

`GET /api/v1/roulette/stream` returns `text/event-stream` with:

```
retry: 3000

id: 1
event: snapshot
data: {"observed_at":"…","round":{…},"recent":[…]}
```

- **Same payload as the JSON snapshot.** Encoding moved to
  `roulette/public_payload.py` so both routes share exactly one projection; a
  field added there becomes public, so no bet, wallet, identity or RNG value may
  reach it.
- **Reveal-gated by construction.** The stream calls
  `read_public_round_snapshot()`, which hides `winning_number` until `reveal_at`
  and reports a persisted-but-unrevealed result as `SPINNING`, never as a void.
- **De-duplicated.** Every poll is fingerprinted on the public `round` and
  `recent` fields only; `observed_at` changes constantly and never forces an
  event. An unchanged poll costs one read and zero client bytes.
- **Bounded.** `MAX_SECONDS = 300` then `event: close {"reason":"reconnect"}`;
  the client reconnects and immediately gets current state. There is no replay
  contract and no client-visible game clock, so a late join never sees a stale
  authoritative result.
- **Heartbeats** are SSE comments (`: keep-alive`) every 15s, so proxies do not
  idle the connection out without producing client events.
- **Capacity.** At most 64 concurrent streams per process
  (`StreamCapacityExceeded` → generic 503). The slot is released in a `finally`,
  so a client disconnect or a database error cannot leak it.
- **Fail closed.** No database URL, an unmigrated schema, or a SQL error yields
  a plain 503 JSON response, never an invented phase. A mid-stream failure emits
  one `event: unavailable` and keeps trying; it never fabricates a result.
- **Headers:** `Cache-Control: no-store`, `X-Accel-Buffering: no` (so a proxy
  does not buffer the stream), `Content-Type: text/event-stream; charset=utf-8`.

## What it is not

No authentication, no per-player data, no bet placement, no bet-lock event, and
no private "your bet was accepted" channel. A private, session-scoped feed
(bet confirmation, balance, forced logout on revocation) is a separate slice and
still needs the trusted reverse-proxy/client-IP decision plus realtime
authorization tests.

## Tests

`tests/test_public_stream.py` (12 cases):

- framing: retry preamble, one snapshot for unchanged polls, `id` increments,
  ordered `BETTING → SPINNING → RESULT` events, bound `close` frame;
- an unavailable reader emits exactly one generic `unavailable` event and no
  snapshot; heartbeats are comments, not events;
- no frame contains `bet`, `stake`, `account`, `wallet`, `balance`, `player`,
  `token` or `csrf`, while the public `winning_number` is present after reveal;
- invalid timing configuration (zero, negative, string, out-of-order intervals)
  fails closed;
- capacity rejects instead of queueing, and `guarded_stream` always releases its
  slot;
- HTTP: 503 without a database, 503 at capacity, and a real streamed response
  with `text/event-stream`, `X-Accel-Buffering: no`, `no-store` and no private
  markers;
- PostgreSQL (rollback-isolated): a `SETTLED` round past reveal appears in
  `recent` with its number, while the newest `CLOSED` round whose reveal is still
  ahead reports `phase=SPINNING`, `winning_number=None`, and never appears in
  `recent`. Run three times consecutively without a database reset to prove
  isolation.

## Live evidence (local, not CI)

A second API instance pointed at the migrated development database streamed
`id: 1 event: snapshot` with `phase=RESULT, winning_number=17`. While that single
connection stayed open, an `OPEN` round was inserted and the same connection
received a second event with `phase=BETTING` — with no event for the unchanged
polls in between. The scratch database was then recreated clean.

## Remaining gates

Authenticated/private realtime channel, bet-lock and bet-accepted events,
reconnect/replay semantics agreed with the client (D-08), a per-source connection
budget that survives multiple API processes (the cap here is per process), and
proxy/buffering behaviour in the real deployment.
