# P11-T03b — gameplay-write attempt windows

Status: **implemented and tested; not deployed.**

## Why

[P11-T03a](P11-T03a.md) exposed an opt-in write route with no abuse budget: a
script holding a valid session could submit thousands of bets per minute. The
authentication guard (`P03-T02i`) throttles *logins*, not gameplay writes, and
a bet is far more expensive than a login attempt (reserve lock, exposure
re-projection, two ledger inserts, one bet insert).

## Scope

Migration `20261103_01` adds `gameplay_write_buckets(key_digest PK,
window_started_at, attempts)` with a 64-hex digest check and a non-negative
check. Only keyed HMAC digests are stored — no session token, account ID, IP
address, selection or stake.

`fairmount_api.roulette.write_limits.guard_gameplay_write()` takes two
pseudonymous buckets in sorted key order before admission runs:

| Bucket | Key | Limit |
|---|---|---|
| Session | HMAC(pepper, `session\0` + SHA-256(token)) | **20** attempts / 1 minute |
| Source | HMAC(pepper, `source\0` + canonical transport IP) | **120** attempts / 1 minute |

The pepper is the existing restricted `FAIRMOUNT_AUTH_HMAC_KEY_FILE`; the route
returns 503 if it is missing. `_direct_source()` supplies the transport-verified
IP, never a forwarded header.

Design points:

- **Attempts, not failures.** A rejected flood costs the same database work as an
  accepted bet, so denials still spend budget.
- **One transaction.** Counting and admission commit together; the admission
  callback runs in a SAVEPOINT so an expected denial rolls back its own side
  effects without releasing the bucket locks.
- **DB clock.** Windows use `clock_timestamp()` after the row locks, so process
  clock skew cannot extend or reset a budget.
- **Expired windows restart lazily** on the next allowed attempt.
- **Throttled responses** are `429 {"status": "unavailable"}` with
  `Retry-After` (1–61s) and `Cache-Control: no-store`; the specific denial reason
  is never disclosed.
- **Lock order** is now documented as buckets → session/account → reserve →
  round → wallet. Settlement, rebate and withdrawal paths never take buckets, so
  no cross-order deadlock is possible.
- **No journal.** Throttled attempts are not appended to an immutable table,
  because D-02 retention is still undecided and a hot write path must not create
  an unbounded audit obligation. Operator visibility is the live bucket row
  (`attempts`, `window_started_at`).

## Tests

`tests/test_gameplay_write_limits.py` (PostgreSQL, 10 cases) — counting and
throttling, `Retry-After` bounds, window expiry restart, source window spanning
sessions, one crowded source not blocking another, expected denial counted with
its savepoint effects rolled back, unexpected errors propagating instead of
looking like denials, nine invalid-context rejections, digest-only storage, and
an eight-thread independent-connection race that permits exactly the limit.

`tests/test_zz_player_bet_api.py` (11 cases, two new) — real HTTP route: three
writes with the session limit patched to 2 give `200, 200, 429`, the wallet is
debited twice, `Retry-After` is present and no token leaks; two rejected
(unaffordable) writes still consume the window and the next write is throttled
with nothing accepted. The route now also requires the restricted HMAC key file;
its absence is covered by the existing 503 configuration test.

## Remaining gates

Limits are per session and per source, not per player across rotated sessions
(one unrevoked session per account bounds that today). Shared-NAT deployments
may need a distinct source policy, which depends on the still-open trusted
reverse-proxy/client-IP decision. No alerting on sustained throttling, no
staging load test, and no operator override.
