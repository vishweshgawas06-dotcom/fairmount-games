# P05-T02b — Private agent↔assigned-player point transfers

**Status:** Internal implementation and local non-DB gates complete (2026-10-23); PostgreSQL CI pending. No API/realtime authorization boundary or public point route.

`fairmount_api.agent_point_accounting.transfer_agent_points` takes a live agent bearer token, a UUID of an enabled **currently assigned** player, direction, full positive integer amount, reason and actor-scoped idempotency key in a caller-owned transaction. It locks the authenticated agent Account/session, player Account, active assignment, then affected wallets in stable UUID order; an owner-managed or another agent's player cannot be acted on. It rejects an unaffordable **whole** transfer, invalid/stale token, disabled player/agent, invalid stake/direction and changed same-key intent. The paired signed journal materializes conserved balances under the PostgreSQL constraints from P05-T01b. A holder password is never needed for an authorized operator transfer, and there is no agent→agent or agent→reserve path.

Existing accepted bets still need later settlement credits even for a disabled player; this ordinary administrative transfer service does **not** implement payout, refund or account recovery. The owner reassignment/disable service must use a compatible lock order before activation to prevent stale assignment races. The request edge still needs login rate limiting/failure audit, cookies/CSRF and resource authorization. Caller must roll back on any error and commit before returning success to the user.
