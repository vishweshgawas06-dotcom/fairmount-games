# P03-T01p — Internal owner MFA enrollment and confirmation

**Status:** Complete for internal owner MFA enrollment/confirmation, 2026-10-19.

**Authorization:** D-03 owner TOTP and ten offline recovery codes; D-12 owner MFA before management; D-15 external encryption key, with broad staged implementation permission. This is internal transaction logic only, not an accessible enrollment or login endpoint.

## Implementation

- `begin_owner_mfa_enrollment(connection, keyring)` requires an enabled OWNER with a permanent password, locks account then credential, creates a fresh TOTP seed encrypted with the active owner-bound MFA key, and stores an unconfirmed factor. It returns the seed in a redacted-repr result; caller must commit before displaying it. Existing factor enrollment is rejected rather than overwriting a live MFA seed.
- `confirm_owner_mfa_enrollment(connection, code, keyring)` locks the same resources and factor, decrypts using its recorded key version, verifies a current TOTP code (±one 30-second step), atomically stores ten distinct recovery-code digests, confirmation/last-used step and an `OWNER_MFA_ENROLLED` event. It returns codes in a redacted-repr result; caller must commit before showing them once. Reconfirmation fails. This function does **not** issue a session or authorize dashboard access.
- PostgreSQL tests cover password prerequisite, encrypted unconfirmed state, successful confirmation and ten digests, wrong code, disabled account, replay and rollback with no partial code/audit state. No plaintext seed, key or recovery code is persisted.
