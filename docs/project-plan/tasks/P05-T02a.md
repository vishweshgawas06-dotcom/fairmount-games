# P05-T02a — Private owner issuance and paired owner↔member transfers

**Status:** Internal implementation and local non-DB gates complete (2026-10-23); PostgreSQL CI pending. This is **not** a public money-moving route or a full P05-T02 completion.

`fairmount_api.point_accounting` accepts a SQLAlchemy connection under a caller-owned transaction and an existing raw owner bearer token. It uses the existing account/session lock and `require_recent_owner_mfa` (≤10 minutes) before writing. Only a currently enabled owner can issue positive integer points into **their own wallet**; only an enabled agent/player wallet may receive an owner-funded transfer or make a normal full-amount return to owner. No wallet holder password is requested. A transfer locks affected account wallets in stable UUID order, checks the **entire** requested debit and destination overflow, and writes one immutable operation plus both signed ledger effects; the migration materializes balances and enforces a paired commit. Neither transfer nor return creates points. Both methods return operation ID and replay status, not a potentially stale wallet balance.

The unique key belongs to the authenticated actor; a SHA-256 request fingerprint over kind, owner, endpoints, amount and canonical reason ensures same-key/same-intent retry is a no-op and conflicting intent is denied. The owner Account lock serializes competing owner actions/retries in the same database; the method does **not** commit for its caller. Routes are absent. Stale MFA, disabled members, invalid amounts/IDs/reasons, wallet insufficiency and duplicate-key changes fail closed. Caller must roll back on error; controller design still needs request throttling/failure audit, cookie/CSRF, step-up UX, privilege separation and a concurrency test involving independent connections before production use.
