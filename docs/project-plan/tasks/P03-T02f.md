# P03-T02f — Internal session logout and append-only audit

**Status:** Complete (2026-10-19); [CI 39207809470](https://github.com/vishweshgawas06-dotcom/fairmount-games/actions/runs/39207809470) passed.

`revoke_presented_session` accepts only a correctly shaped bearer token, finds its SHA-256 digest, locks Account → AccountSession in the same order as validation/login, and revokes an unrevoked session even if its account is disabled or its idle/absolute deadline has elapsed. A repeat, malformed, unknown or already-revoked token is a no-op. The caller must commit before acknowledging logout. A successful revocation appends one token-free `SESSION_REVOKED` security event with the account as actor and target; actor attribution means **bearer possession**, not fresh MFA. Alembic revision `20261019_04` expands the event whitelist. No raw token is stored or logged. Future-issued corrupt session timestamps are handled without violating the DB check by setting revoked time to at least issued time; the event uses actual DB time.

**Boundaries:** There is no logout route, cookie clearing, CSRF check, proactive revocation on disablement/password changes, or realtime disconnect. Future HTTP logout must clear the cookie even for an already invalid token and require CSRF protection. A session row must be checked again on every HTTP/realtime operation; merely marking it revoked is not enough to close an already-authorized open socket. D-03's affected-session revocation on account changes remains a separate gate. D-02 log retention is unresolved: no cleanup is introduced. Downgrading an event constraint after immutable logout events requires an explicit retention review.
