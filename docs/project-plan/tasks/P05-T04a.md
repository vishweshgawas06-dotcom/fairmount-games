# P05-T04a — owner/agent point and reserve HTTP writes

Status: implemented and tested, **opt-in direct TLS; no production deployment**.
Date: 7 November 2026.

## Route contract

All routes are `POST`, use exact JSON schemas and the existing same-origin
cookie/CSRF, bounded-body, UUID idempotency and attempt-window pipeline:

| Route | Required body | Authority |
|---|---|---|
| `/api/v1/operator/points/issue` | `amount`, `reason` | Fresh-MFA OWNER; credits only owner wallet |
| `/api/v1/operator/points/transfer` | `identifier`, `amount`, `to_member`, `reason` | Fresh-MFA OWNER; conserved owner↔enabled agent/player |
| `/api/v1/agent/points/transfer` | `username`, `amount`, `to_player`, `reason` | Live enabled AGENT; conserved agent↔currently assigned enabled player |
| `/api/v1/operator/reserve/fund` | `amount`, `reason` | Fresh-MFA OWNER; conserved owner→reserve |
| `/api/v1/operator/reserve/withdraw` | `amount`, `reason` | Fresh-MFA OWNER; proven surplus reserve→owner |

Positive integer amount up to signed BIGINT, actual boolean direction flags,
nonblank printable reason up to 500 characters; no target/source/role overrides
or holder password. Reasons flow to the existing immutable point-operation
journal, not a new general-purpose log. No real money is supported.

## Atomicity, authorization and replay

Authenticate the live actor before lookup/replay; route kind determines role,
never request data. Inside the existing write-guard savepoint invoke the tested
ledger services. Persist the HTTP request UUID as a namespaced internal point
operation key and append the non-secret actor receipt in the **same outer
transaction** as the ledger and wallet/reserve projection changes. Render only
after commit. Same key/body returns the same opaque operation ID without moving
points again; changed key parameters/action conflict. A database fault rolls back
the operation, journals, projections and receipt, not merely the response.

Only explicit issuance changes supply. Transfers/funding/withdrawal conserve it.
The full source balance must cover the request; no partial transfer and no
negative balance. Agent scope is read under the existing account/assignment
locks; a reassignment or player disablement blocks new ordinary transfers.
No agent issuance, reserve management, cross-agent operation or owner-managed
player access is introduced.

Reserve withdrawal calls the existing reserve-serialized POOL-01 surplus
primitive. It must retain worst-case accepted payouts **and full-void-refund
coverage** over every unsettled round. Reject the new withdrawal, never revoke
accepted bets, change RNG or withhold winnings. No result-selection code or
exceptional-void route is wired by these adapters.

## Verification

Eight additional committed HTTP tests extend `tests/test_zz_operator_api.py`
(38 total):

1. Owner issuance and exact operation actor/reason; replay credits once, conflict refuses.
2. Owner→agent→player and return flows with exact balances and conserved totals.
3. Full insufficient-transfer rejection, live reassignment and disabled-player freeze.
4. Integer/boolean/reason schemas, agent issuance/reserve denial and stale owner MFA.
5. Reserve funding/replay/surplus return conservation and unaffordable withdrawal denial.
6. Concurrent same-key owner transfer: two responses, one operation and one debit.
7. Injected receipt failure rolls back issuance/ledger/projection; same-key retry succeeds.
8. Accepted funded bet followed by HTTP full-reserve withdrawal: denied, accepted stake
   remains immutable and wallet/reserve balances unchanged.

Local full fresh PostgreSQL unittest: **326 passed, zero skips**; separate fresh
pytest **415 passed**, three Node wheel cases, metadata parity (`alembic check`),
Ruff, diff checks and Markdown links passed. Supported Python 3.12 CI is watched
after push.
