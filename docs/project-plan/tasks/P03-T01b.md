# P03-T01b — Canonical identifiers and PostgreSQL constraints

**Status:** Complete for the authorized identifier/DB slice, 2026-10-16.

**Authorization:** On 2026-10-16 the owner approved the P03-T01a contract and explicitly authorized this *narrow* code slice: canonical identifier helpers, PostgreSQL uniqueness/validation migration and tests. No registration endpoints, credentials, sessions or wallets.

## Implementation

- Pure helpers validate/canonicalize player usernames (lowercase) and Agent IDs (lowercase for storage; uppercase display); Agent IDs use `secrets.choice` over the approved alphabet. These helpers do not reserve a name or create an account. A future provisioning transaction must retry a generated ID after a unique conflict; never treat it as a secret.
- Migration `20261016_02` adds nullable `private_identities.login_kind` with allowed `PLAYER`/`AGENT` identifiers or both login fields null. An explicit non-null guard avoids SQL NULL/CHECK bypasses. PostgreSQL `COLLATE "C"` ASCII regex checks canonical lowercase, length, reserved words/prefix and Agent-ID alphabet; a partial unique index on `(login_kind, login_identifier)` guards duplicates, even across agents. Mobile remains non-unique. Null login fields remain valid for pre-activation/legacy records.
- Existing non-null identifiers without `login_kind` **block** migration rather than being dropped or silently classified. A populated deployment must first review and backfill its data in a separately approved migration plan. Downgrade drops only the added column/check/index; never run a downgrade casually on production data.
