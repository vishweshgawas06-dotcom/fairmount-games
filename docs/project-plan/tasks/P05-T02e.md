# P05-T02e — Owner-only surplus reserve withdrawal

**Status:** Private implementation/local non-DB checks passed (2026-10-23); PostgreSQL CI pending. No public reserve API.

`withdraw_surplus_reserve` requires a live owner session with fresh MFA, validates a positive **whole** requested amount and reason, and supports actor-scoped idempotent replay/conflict detection. Holding the global reserve lock shared by bet admission, settlement, refunds and deposits, it rebuilds every OPEN/CLOSED round's approved POOL-01 worst-result/full-void exposure from persisted immutable bets. It then rejects the *entire* withdrawal unless post-withdrawal reserve covers **all** unresolved rounds. It also checks owner-wallet overflow and records a paired reserve-debit/owner-wallet-credit journal operation; it never issues points or pays a player. No RNG inputs or outcome rewrite. Lock order is owner Account/session → reserve → owner wallet, consistent with owner deposits; other betting/settlement transactions take reserve before round/wallet. Disabling/closing a round alone does not release its liability; terminal financial accounting does.

PostgreSQL tests check an accepted straight-up winning liability rejects a withdrawal, a separately owner-funded surplus can be removed exactly once and idempotency conflicts reject, invalid player actor rejects, full-void-refund exposure is retained even when every number's payout is smaller, and reconciled supply remains unchanged. This is a private primitive: request-edge authorization/rate limiting/failure audit, withdrawal/admission races and privileged direct SQL separation are not yet proved. Never expose it as a route before those gates.
