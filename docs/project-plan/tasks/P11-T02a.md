# P11-T02a — Private player-specific, all-or-nothing rebet

**Status:** Local checks and [CI 40082697980](https://github.com/vishweshgawas06-dotcom/fairmount-games/actions/runs/40082697980) passed (Python 3.12/PostgreSQL, 2026-10-24). No public rebet route or client control.

`roulette/rebet.py` reads the authenticated player's **entire immutable accepted set** from the immediate prior persisted round, including separate duplicate records. It does not trust client-supplied positions or stake amounts. On a new target round it locks player Account/session → global reserve → target round → wallet, checks DB cutoff and affordability of the **full aggregate requested** set, validates every legal position/chip and full per-number/per-selection cap without a cap-limited partial item, then projects **the entire package at once** into POOL-01 across all unsettled rounds. A bundle that is not wholly affordable, cap-legal and funded is rejected without inserting any bet or debiting points. A successful bundle inserts one immutable `BET_STAKE` operation and paired wallet→reserve journal effects per item within a SAVEPOINT in the caller's transaction. Each item has a stable actor-scoped derived key. The complete accepted set can be replayed after cutoff without moving points again; reusing the request key for a different target conflicts. The caller must commit before confirming success.

PostgreSQL tests cover two-item success/replay after cutoff, full-wallet rejection, a cap that would have yielded a partial normal bet, global underfunding against an existing target liability, and journal reconciliation. This is not yet proof for all duplicate combinations, two-connection rebet/cap races or repeated-round performance. No autonomous worker or HTTP route calls it. Auth/rate-limit/CSRF/request-edge handling and UI feedback remain later gates.
