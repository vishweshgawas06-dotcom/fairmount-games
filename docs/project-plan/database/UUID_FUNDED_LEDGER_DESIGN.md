# P05-T01 — UUID wallet, immutable ledger and funded reserve design

**Status:** Engineering design checkpoint, 2026-10-23. No new database tables, wallet service, authorization or money-moving route yet. This refines [D-10](../decisions/2026-10-15-account-provisioning-and-point-flow.md), [D-01](../decisions/2026-10-15-account-disable-and-reassignment.md) and [POOL-01](../decisions/2026-10-19-funded-reserve-solvency.md); it does not replace their product rules.

## Data shape and migration order

- Preserve `accounts.id UUID` and **all** existing identity/MFA/session/security-event tables and revision history. Add an Alembic child of the current identity head; do not merge `main`'s independent BIGINT `0001_initial_schema` or take its ORM wholesale. A wallet has a UUID FK to exactly one existing account. A *single distinct game-reserve row* is not an `Account`, has no login/credential or owner-managed balance, and can only be moved via authorized ledger operations. Create zero wallets for existing accounts, and guarantee zero-wallet creation for future account provisioning without an implicit mint; test local bootstrap as well as owner/agent/player creation.
- Use integer points with DB nonnegative `BIGINT` balance and positive operation amounts; explicitly guard aggregate arithmetic against signed-64-bit overflow. A zero reserve begins unfunded. Do not call reserve replenishment issuance: owner issues into **owner wallet**, then separately transfers already-owned points to reserve.
- One operation journal row has immutable UUID operation ID, type, actor UUID/role, reason, idempotency key scoped to actor and operation intent, created timestamp and durable source/destination/reference data; replay must compare the **full intent** (type, source, target, amount, reason/round context) before returning an existing result. A changed request with the same key conflicts; concurrent retries serialize. No raw password, MFA seed or bearer token is recorded.
- Every effect is an immutable signed ledger entry linked to its operation ID and exactly one wallet or reserve, with immutable round/bet reference where applicable. Issuance has one positive owner entry and is the **only** operation that increases global point supply. Each transfer/stake/payout/refund has exactly two linked effects: source `-amount`, destination `+amount`, so its net is zero. A correction is a new authorized reasoned operation, never a mutation/deletion of history. Never reuse `main`'s `admin_adjust` direct credit/debit of arbitrary wallets.
- Maintain a materialized balance with one locked ledger-backed update per effect in the same DB transaction and a reconciliation query that compares each balance with the sum of its immutable effects. Include the reserve in global conservation. DB constraints/triggers must prevent negative balances, immutable-entry edits and duplicate effect/idempotency IDs; tests must prove paired-or-nothing operations and rollback on the second effect. Decide and verify how the DB guards balance changes not backed by the journal before claiming append-only accounting.

## Authoritative operations and authorization gates

| Operation | Actor and required source → destination | Replay/exception rule |
|---|---|---|
| `OWNER_ISSUE` | Currently enabled owner with valid MFA/10-minute step-up → **owner wallet only** | Reason required; explicit total-supply increase; cannot issue to agent/player/reserve. |
| `OWNER_TRANSFER` | Owner wallet ↔ any enabled agent/player wallet | Owner action, paired entries; owner removal debits recipient's full amount; no holder password required. Disabled-player normal removals blocked. |
| `AGENT_TRANSFER` | Enabled agent wallet ↔ enabled **currently assigned** player | Assignment/role/status rechecked and locked in same transaction; neither owner-managed players nor other agents' players; no sub-agent funding by agent. |
| `RESERVE_FUND` / `RESERVE_WITHDRAW` | Owner wallet ↔ distinct reserve | Owner-authorized, reasoned; withdrawal is permitted only if remaining reserve covers all unsettled obligations in the same lock. No automatic/hidden issuance. |
| `BET_STAKE` | Enabled player wallet → reserve | Server-side canonical validated selection, cap-approved accepted stake, cutoff, idempotency and POOL-01 candidate projection all checked atomically **before** committing. Wallet must afford full requested stake before cap-limited partial acceptance; reserve insufficiency rejects candidate in full. |
| `PAYOUT` / `VOID_REFUND` | Reserve → player wallet (including a disabled player for already-accepted bets) | Each accepted bet can reach exactly one terminal branch; payout uses approved *total return*, refund returns full stake. Idempotent round settlement/void and immutable outcome; do not enforce a disabled-account block on owed credits. |
| Agent disable/reassignment | Owner action, separate audited assignment change and return of unused agent wallet funds to owner | Old agent's privileges terminate atomically; historical bets/ledger actors unchanged; no automatic movement of players' balances. |

These are **internal service contract designs**, not routes. Before HTTP/WebSocket exposure, implement request-boundary rate limiting/failure audit, cookie/CSRF controls and role/assignment/resource session checks; owner issuance/funding/withdrawal require valid recent step-up. All ordinary transfers reject the **whole** amount if source funds are short, never overdraft or partial admin transfers.

## Concurrency and solvency invariant

The single reserve row (or a separate global admission lock acquired **before** all conflicting round/wallet locks) serializes bets across players/rounds, reserve withdrawals and obligations released by terminal settlement. Specify and test one global order: admission/reserve lock → affected round and assignment/status rows → account wallets in stable UUID order → per-number/selection exposure/idempotency rows. Locking and status checks must be reviewed for deadlock-free disable/reassignment and owner funding. If some operation needs an incompatible order, redesign it before enabling any routes. Use PostgreSQL transactions/`FOR UPDATE`; no optimistic unprotected balance reads or client-supplied exposure vectors.

For unsettled round `r`, derive `O(r) = max(full accepted-stake refund, max over 0..36 of total payout)` **from persisted bets** plus exactly one candidate, using the [pure projector](../../../services/api/src/fairmount_api/reserve_coverage.py). Sum independent round obligations. After the candidate stake transfer, require `reserve_balance + accepted_stake >= sum(O(r))`. If false, roll back the whole prospective bet (including idempotency/ledger/caps). Existing accepted bets remain binding. A withdrawal must check `reserve_after >= sum(O(r))`. Settlement/void must debit the reserve for exactly the actual payout/refund and release only that terminal round's obligation, without creating points or selecting a low-liability outcome. No arbitrary retry cutoff, forced void or outcome re-roll while D-06 is open. On unexpected shortfall, stop admission and alert owner; never skip an accepted win.
