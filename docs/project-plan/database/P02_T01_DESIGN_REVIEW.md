# P02-T01 — Conceptual design review

**Status:** Technical self-review completed; owner review pending. This is not an independent review, schema approval, implementation permission or proof of PostgreSQL behavior.

**Scope reviewed:** [Conceptual schema and transactions](CONCEPTUAL_SCHEMA_AND_TRANSACTIONS.md), [D-01](../decisions/2026-10-15-account-disable-and-reassignment.md), [D-02](../decisions/2026-10-15-privacy-deletion-and-retention.md), [D-10](../decisions/2026-10-15-account-provisioning-and-point-flow.md), the approved roulette specifications, and [P02-T01 task gates](../tasks/P02-T01.md).

## Findings and disposition

| ID | Risk / finding | Proposed resolution and status |
|---|---|---|
| R-01 | The acceptance sketch said to lock player wallet and exposure counters before checking pool capacity; the general lock order requires **all wallet rows, including the reserve**, before counters. Inconsistent lock orders can deadlock or read a stale reserve. | **Corrected in the conceptual draft:** lock player/reserve wallets in stable order before exposure keys and evaluate reserve only under the same transaction. PostgreSQL race/deadlock tests remain required; no locking strategy has been proven. |
| R-02 | `SELECT FOR UPDATE` cannot lock an exposure row that does not exist yet; same-key inserts can race. Idempotency keys also need safe first-writer handling. | Already noted in draft: propose pre-seeded rows or unique insert/upsert plus conflict handling; define the exact database protocol and retry/error path in a later implementation task. **Open until PostgreSQL tests.** |
| R-03 | A unique entry per bet+effect kind does not alone forbid a `PAYOUT` **and** `VOID_REFUND` for the same bet. Workers can race. | Require every settlement/refund writer to serialize through the round's terminal row and write terminal state plus all effects in one transaction; consider an additional database-enforced terminal/effect invariant during physical schema review. **Open until real concurrent tests.** |
| R-04 | Owner-funded game reserve may be underfunded if multiple accepted bets across players can win simultaneously, if a second round opens before the prior one settles, or if the owner withdraws reserved points. One player's 2,000-point caps do not bound *global* payout. | **Blocking POOL-01 product rule before bet implementation:** owner must approve a prospective all-outcomes coverage/withdrawal policy, including outstanding-round liabilities and disclosure of any rejection. Do not add a hidden global cap, force a losing result, or withhold an accepted payout. A candidate inequality is reserve available after candidate stake and prior commitments ≥ maximum net payout across possible outcomes; the exact formula, bookkeeping and concurrency protocol are **not approved**. |
| R-05 | Full global-round settlement is approved as one transaction, but locking all affected wallets may exceed the 60-second reveal boundary under load or contend with allocations/transfers. | Preserve atomic rule. Design a server-time/worker recovery plan (D-06), define operational SLOs (D-04/OPS-01), and test scale before implementation. If timing cannot be met, seek owner decision rather than silently settle players in separate commits. **Open.** |
| R-06 | “One active player session” cannot be enforced using a partial index whose predicate depends on the changing current time; sessions may expire without an index update. | **Clarified in the conceptual draft:** use explicit active/revoked state or a unique current-session pointer maintained by a serialized login/revocation transaction, with expiry checked at authentication. Test two simultaneous logins and stale WebSocket connections. Physical choice still open. |
| R-07 | Owner-managed players have no agent assignment, but other queries might assume an agent FK exists. An agent disabled or reassigned during a transfer could keep stale authority. | Use explicit owner-managed access path, optional active agent assignment, server-side ownership checks within transfer/reassignment transaction, and tests that former agents and other agents cannot access those players. **Open until authorization tests.** |
| R-08 | Wallet balance projection, paired transfers, issuance, stakes, payouts and refunds require distinct accounting sources and reconciliation. A transfer is not issuance; a lost stake moved to reserve cannot be debited a second time. | Proposed owner-only issuance event, paired transfer and game-pool ledger types are documented. Design concrete uniqueness constraints, immutable ledger rules and total-supply reconciliation in P05 and prove them with PostgreSQL integration tests. **Open until implementation.** |
| R-09 | D-02 retention periods, login identifier reuse after anonymization, deletion eligibility and backup expiry are undecided. Unique username/mobile and audit links can re-identify an account. | Keep identifiers separated, limit access; do not promise irreversible deletion, finalize destructive migrations or implement cleanup until owner/legal/operations review. **Open by owner choice.** |
| R-10 | The approved payout convention is **not** conventional casino total return (e.g. 10 straight-up wins 350 total rather than 360; even-money win credits only the original stake). A “standard European roulette” label could mislead users. | Preserve the approved specification for now. Obtain explicit product-facing wording/disclosure review before player UI or launch; no payout change is authorized by this review. **Open for UX/owner review.** |

## Review gate and next action

- The conceptual record groups and transaction paths cover the known product rules at a **design level**, subject to the open items above. R-01 and R-06 are consistency corrections to the draft, not implemented fixes.
- **Owner review still needed**: confirm whether this conceptual structure is a suitable baseline for future small implementation tasks, acknowledge that POOL-01 and D-06 remain blockers for betting/settlement, and do not mark those rules approved merely by approving the design baseline.
- P02-T01 remains **open pending owner review**. Subsequent implementation would require a separately authorized scoped task, a standard PostgreSQL test environment and migration review. No database, concurrency, security or gameplay code/tests were produced here.
