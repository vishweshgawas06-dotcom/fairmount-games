# P03-T01i — Minimal security-event audit boundary

**Status:** DB-only slice complete 2026-10-16; [CI run 38867010258](https://github.com/vishweshgawas06-dotcom/fairmount-games/actions/runs/38867010258) passed. No service writes events yet.

`security_events` is append-only in normal database operation. Each row records an event type, source, target account, optional attributed actor account, server timestamp and opaque event UUID. An activation event attributes possession of a provisional secret to its account; its actor ID is **not proof of a fully authenticated session or MFA**. The schema deliberately has **no free-text reason, request body, password, secret, digest, hash, phone number, TOTP seed or recovery code column**. Direct SQL permissions must still be restricted in deployment; a privileged DBA can change schema/triggers, and this is not a certified audit system.

A null actor is permitted only for the trusted owner-run **local bootstrap/reissue** events before in-app authentication exists. The `LOCAL_CLI` source alone does not establish that the owner ran the command; that must be enforced by owner-only deployment-shell access and CLI security review. All other event types require an actor account reference; future system-originated events need their own explicit policy. The target must be an existing account, so owner bootstrap must create the owner row and event together in one transaction. Later agent/player issuance and activation transactions must write their appropriate audit event in the same transaction as credential state changes.

The event-type vocabulary is intentionally narrow (`OWNER_BOOTSTRAP_ISSUED`, `OWNER_BOOTSTRAP_REISSUED`, `INITIAL_CREDENTIAL_ISSUED`, `INITIAL_CREDENTIAL_CONSUMED`, `PASSWORD_CHANGED`, `OWNER_MFA_ENROLLED`). Adding reset/recovery/session events later requires a migration and service-level authorization review. The DB check cannot prove which user clicked an action or that MFA was recent; it only records structurally valid, immutable rows. Audit coverage for failed attempts, rate limits, browser request correlation, data access and wallet/ledger operations is future work and must not be inferred from this table.

D-02 retention/deletion/backup and privacy minimization are still open. No audit cleanup, export, truncation or anonymization procedure is implemented; a later approved lifecycle may require a separate migration. PostgreSQL tests cover valid/invalid actor/source/target combinations, exact minimal columns, update/delete/truncate guards and migration round-trip. This is not registration, owner bootstrap, login or MFA behavior.
