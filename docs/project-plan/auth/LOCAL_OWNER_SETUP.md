# Local owner setup — development-only safety notes

**Status:** P03-T01q connects internal owner transactions to a terminal-only local CLI. This is **not** a production deployment or dashboard-login procedure. The repository's DB adapter only permits localhost `fairmount_dev`/`fairmount_test`, and this CLI explicitly selects `fairmount_dev`. No owner login/session endpoint exists.

The owner must control the local deployment shell and terminal personally. Do not run these commands through CI, redirected output, a screen recorder, shared terminal, chat, shell transcript or a log-capturing supervisor. Use an isolated, secure terminal; protect its scrollback. The CLI rejects non-TTY streams. Commands take no secret arguments—passwords, initial secret and live TOTP code are entered through hidden prompts. Never paste a credential or encryption key into a ticket, chat, source file or Git commit.

From a configured local installation with the PostgreSQL service running and a private `.env` (see infrastructure README), **only for development**:

1. `FAIRMOUNT_DB_NAME=fairmount_dev python -m fairmount_api.identity.owner_setup_cli init` creates the sole OWNER row, a pending 24-hour digest and an audit event. It prints a one-time secret **after DB commit**. If that output is lost before activation, `reissue` rotates the pending digest and invalidates the old secret; it cannot run after activation or MFA enrollment.
2. `FAIRMOUNT_DB_NAME=fairmount_dev python -m fairmount_api.identity.owner_setup_cli activate` prompts for the initial secret and a new 12–128-character passphrase. Expiry is checked against PostgreSQL's clock on both sides of hashing. It sets a permanent password and consumes the secret. **This still grants no access.**
3. Before enrollment, provide a restricted, owner-owned secret file outside the repository and database via `FAIRMOUNT_MFA_KEY_FILE`. The [key loader](../tasks/P03-T01m.md) requires a regular 0600-or-stricter file containing strict JSON with an active version and a standard-Base64-encoded 32-byte random key; keep a protected offline backup and never put the key in `.env` or Git. Example *shape only*, not a usable key: `{"active_version": 1, "keys": {"1": "<base64 of 32 random bytes>"}}`.
4. `FAIRMOUNT_DB_NAME=fairmount_dev python -m fairmount_api.identity.owner_setup_cli enroll` commits an encrypted pending seed, then shows that seed once. Configure an authenticator privately. `confirm` prompts for a current six-digit code, commits ten one-way recovery-code digests, and only then shows the ten codes once. Store codes offline; never paste them into chat. **No owner session or dashboard exists yet.**

If post-commit terminal output fails, do **not** blindly rerun a command. An already committed `init` may be repaired with pre-activation `reissue`; a lost *unconfirmed* seed or confirmed recovery-code output has no safe rotation/replacement command yet. Preserve the authenticator/key backups and wait for the separately reviewed recovery flow. If all owner factors/codes are lost, D-03 explicitly forbids a self-service bypass. Production deployment must add guarded setup/retry procedures, key rotation and backup rehearsal, rate limits, owner MFA/session gates and security review before use.
